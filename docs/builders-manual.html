Finding a boundary that isn't there

Two pieces of software. One draws a farm plot on satellite imagery; the other stands in that field and shows you where its edges run, through the camera, with no signal and no ARCore. This is how both work, and why each part is built the way it is.

Sheet 01

The problem

A field agent is dispatched to plot PLT-7013. The boundary exists — as eight pairs of coordinates in a database. On the ground it is marked by nothing at all.

Farm plots in most of India are not fenced. They are separated by a footpath, a change of crop, or an agreement between two families. An agent arriving to inspect one faces three questions in order, and the tooling answers none of them well:

  • Which field is mine? A pin on a maps app puts a dot at the centroid. Standing in a row of six visually identical rectangles, a dot fifty metres away does not tell you which one it belongs to.
  • Where does it end? This is the question that costs money. Fertiliser applied ten metres past a boundary is applied to somebody else's crop, and a yield estimate that includes a neighbour's headland is wrong before anyone has done any agronomy.
  • Which part of it is failing? Satellite imagery can already answer this from orbit. It arrives as a raster on a laptop in an office, and the agent standing on the actual soil has no way to know they are looking at the bad patch.

Why the obvious answers were rejected

ARCore Geospatial API. Google's own answer to this, and genuinely excellent — where it works. It resolves your pose by matching the camera against Street View imagery, so it needs Street View coverage, a live network connection at the moment of use, and a Play Services download. Rural farmland has none of the first and unreliable amounts of the second. A tool that degrades to nothing at the site it was built for is not a tool.

RTK / external GNSS. Centimetre accuracy, and the correct answer if someone is paying for a survey. It is a second device, a subscription to a correction network, and a training burden, for a job whose tolerance is a couple of metres.

A better map screen. Cheap and already tried. Looking down at a top-down map and then up at a field requires the agent to do the projection in their head, which is exactly the step that goes wrong.

Sheet 02

The solution

Draw the boundary where it actually is — standing up, in the camera, at the right distance — using only the sensors every Android phone already has.

The system is deliberately split in two, and the split is the most important architectural decision in the project:

Web tool
Creates truthBoundaries are drawn here and only here. The phone is read-only.
Mobile app
Finds truthCaches boundaries, then locates them on the ground with the radio off.

One writer means there is never a merge conflict between two people's idea of where a fence runs. It also means the phone can be built as a pure consumer: no editing UI, no conflict resolution, no upload queue for geometry. What it does need is to work at the bottom of a field with one bar of signal, which is why everything it draws comes out of a local database.

Why this helps, concretely

  • It works where the crop is. No Street View, no live network, no vendor AR runtime. Sync at the office or at the gate; the visit itself needs nothing.
  • It runs on the phone the agent already carries. Minimum Android 8.0, ~13 MB installed. No hardware to procure, lose or charge.
  • It shows a shape, not a point. An outline can be matched against the real hedge line, which means the agent can confirm the app is right — and catch it when it is wrong. A pin offers no such check.
  • It carries the crop-health layer to the soil. The stressed patch stops being a picture in an office and becomes ground you can stand on, with a numbered marker telling you which one to walk to first.
  • It is honest about its own error. Every reading carries where the heading came from, how old it is, and the expected error in degrees. Near a boundary the drawn edge widens to the live GNSS accuracy rather than pretending to a crisp line.
Stated plainly

The crop-health values in the system today are synthetic — deterministic noise seeded from the plot id, shaped to produce a healthy field with one or two stressed patches. They are not derived from satellite imagery. Every API response carries synthetic: true and a note saying so, and the app labels it on screen. Wiring real Sentinel-2 NDVI means replacing one function, syntheticNdviSampler; nothing downstream of it knows where the numbers came from.

Sheet 03

How the web platform works

Three npm workspaces — shared, service, web — where shared is the geometry both of the other two are compiled against, so the browser and the server can never disagree about an area.

Drawing a plot, click by click

The map screen is MapLibre GL rendering a bare raster style: Esri World Imagery and nothing else. No basemap labels, because a farm boundary is matched against hedges and irrigation channels, not against place names.

All drawing interaction lives in a controller class outside React. The map owns the DOM; React only renders the numbers the controller reports. That separation exists because MapLibre and React both want to own the same canvas, and letting React re-render vertices produced dropped clicks.

What happens on save

The browser POSTs the ring. The server does not trust a single number in it.

  1. Validate. One validator, in shared, run by both sides: ring closed, at least three distinct vertices, no self-intersection, area greater than zero and under the 500 ha ceiling, name and note within length limits, access point a real lat/lng.
  2. Recompute. Area and centroid are calculated server-side from the ring with Turf and written from that calculation — never taken from the request body. A client that lies about its area cannot persist the lie.
  3. Store once. The boundary goes into PostGIS as geography(Polygon,4326). Bounding boxes, radius searches and distances are derived from it by PostGIS on demand rather than stored alongside, so there is no second copy to drift. area_sq_m is the one persisted derivative, because it is the number a surveyor agreed to — and a CHECK constraint rejects any row whose stored area differs from the true geodesic area by more than 1%.
  4. Assign a colour. fieldar.pick_colour_index() picks a palette slot 0–7 that no other plot within 500 m is using, so adjacent plots are never the same colour on screen. The database stores the slot number, not the colour — re-theming both clients is then a palette edit, not a data migration.
Migration policy

Everything lives in its own fieldar schema. Every statement is CREATE … IF NOT EXISTS or CREATE OR REPLACE; there is no DROP TABLE, TRUNCATE or DELETE anywhere in the migrations. Running them against a Supabase project that already holds other data is a no-op on that data.

The health raster

GET /api/plots/:id/health builds the grid on demand and caches it by (plot, capture date, cell size). Because the sampler is deterministic, that cache key is complete — the same plot always produces the same raster, so the cache never has to be invalidated. The grid, the severity banding and the hotspot clustering all live in shared, which is what a real Supabase ingest job would call too. That is the reason they are there rather than in the route: the map and the database must never disagree about which cell is stressed.

Sheet 04

How the mobile app works

Every read goes to the local database and nothing on screen ever waits for the network. Sync is a separate, explicit action that refills the cache when there happens to be signal.

Open the app and you get a list of cached plots. Pick one, tap Find in AR, and the camera opens. From that moment three independent streams are running, at three very different rates, and the entire app is the business of turning them into pixels that sit still.

The frame loop

There is no render thread and no game loop. A new pose or a new fix updates a StateFlow, Compose recomposes, and the canvas redraws. The pose stream is published only on the carrier sensor tick, not on both rotation sensors, because every emission rebuilds the overlay — several hundred ground cells reprojected — and a magnetic sample changes the drawn attitude by nothing at all.

One thing worth being precise about, because it is the question the team will ask first: the camera does not detect anything. There is no image processing, no feature tracking, no plane detection, no SLAM. The camera is a backdrop. The app knows where it is from GNSS and which way it is pointing from the gyroscope, and it projects known coordinates onto the preview using the lens's real focal length. That is why it works in the dark, in fog, and facing a blank wall — and equally why it cannot correct itself by looking at the scene.

Sheet 05

The logics, one by one

Ten pieces of reasoning that between them account for nearly all of the code that is not UI. Each is here because a specific thing went wrong without it.

01 · Local metric frame (ENU)

core/geo/Enu.kt · shared/src/constants.ts
What it does

Converts WGS84 degrees into a flat East–North–Up frame in metres, anchored at one GNSS fix. Every distance, bearing, projection and filter in the app runs in that frame. Degrees are converted once, at the edge, and never used for arithmetic again.

Why it exists

A degree of latitude is 110,540 m everywhere. A degree of longitude is 111,320 m at the equator and about 108,600 m at Mandya. Anything computed in raw degrees is therefore wrong by a different amount on each axis — a grid built that way is visibly rectangular instead of square, and a variance expressed in degrees would make a Kalman filter anisotropic for no physical reason.

The frame is immutable. Moving the anchor means constructing a new one, which makes it impossible to convert two points against different origins by accident. Once the agent has walked 50 m from the origin, the frame re-anchors: the estimate and its variance are physical quantities and survive untouched, so re-anchoring is invisible on screen.

This is the answer to "how do I compute the distance"

Subtract the two positions in degrees, scale each axis by its metres-per-degree, then take the hypotenuse. That is distanceM(from, to) in four lines. The equirectangular approximation is accurate to well under a metre at the few-hundred-metre ranges this app works over — far inside the GNSS error it is drawn against. On the web side, where there is no real-time budget, distances and areas are geodesic instead, computed by Turf on the ellipsoid.

02 · Pinhole projection and near-plane clipping

core/geo/Projection.kt
What it does

Turns a ground coordinate into a screen pixel. Translate the point into the camera's frame, rotate it into device axes with the sensor's own rotation matrix, then divide x and y by depth and scale by the focal length in pixels.

Why it exists in this form

The focal length is not guessed. CameraCharacteristics gives the physical sensor size and the lens focal length in millimetres, from which the true field of view follows; the app logs it on startup so it can be read off a real handset. Assuming a typical FOV instead scales the entire overlay by whatever the error is, which reads as the boundary being at the wrong distance.

Two details are load-bearing. The camera position is a required argument with no default — an earlier version took only the rotation and silently placed the camera at the frame origin, which welded the boundary to the anchor so it appeared to travel alongside the agent while the distance label counted honestly down. Points behind the camera must be culled, because a negative depth mirrors them into the frame in front: the field behind you renders on top of the field you are looking at.

Culling alone is not enough for a polygon. If the agent stands inside the plot and you simply drop the two corners behind them, the remaining outline closes across the middle of the field. So the ring is clipped against the near plane instead, introducing new vertices on the plane — Sutherland–Hodgman, and the reason walls are wound as quads.

03 · Position stabiliser

core/geo/PositionStabilizer.kt
What it does

A constant-position Kalman filter, one scalar filter per horizontal axis, gated by a zero-velocity detector — the standard construction from pedestrian navigation, not an invention. Two numbers produce the whole behaviour: process noise says how fast the true position may be changing (2 cm/s standing, 1.6 m/s walking), and measurement noise is the receiver's own reported accuracy, squared.

Why it exists

A raw GNSS fix wanders several metres from one second to the next even on a phone lying motionless on a wall. Fed straight into the camera pose, the boundary swims — which a farmer reads as "the app does not know where my field is", and they are not wrong to read it that way.

Standing still, the estimate's variance stays small, the Kalman gain collapses toward zero, and new fixes barely move the estimate. Walking, the variance opens up and the estimate tracks. There is no threshold to tune between the two.

Three guards around it

Accuracy floor. Android receivers routinely claim 1 m when the true error is several. No measurement is ever treated as sharper than 3 m, or the filter becomes over-confident and starts ignoring good fixes.

Outlier gate. An innovation beyond 3σ is rejected and the estimate held — but only for four consecutive fixes or five seconds, whichever comes first. A count alone is not a bound: four samples is four seconds at 1 Hz and forever at 0 Hz, which would strand the estimate on a stale position after one wild fix.

Slew limiter. The newest piece, and the one that closed out field testing. The Kalman estimate is built to be unbiased, which is right for an estimator and wrong for something a person is looking at: each fix nudges it a few centimetres and the overlay twitches with it. So the drawn position was separated from the estimate. The estimate tracks the receiver; the drawn position chases it at 8 cm/s while stationary, 2 m/s while walking, and snaps outright past 10 m so a genuine relocation is not hidden. The cap is on distance along the line to the estimate, not per axis — a per-axis cap lets a diagonal correction travel √2 times the intended rate and bends the path toward the axes, which is visible as the overlay sidling rather than sliding.

04 · Orientation smoother

core/geo/OrientationSmoother.kt
What it does

Spherical interpolation between quaternions with a time constant that adapts to how far the estimate has fallen behind — the 1-euro filter (Casiez, Roussel & Vogel, CHI 2012) applied to attitude. Heavy when the phone is nearly still (τ = 0.65 s), light when it is being turned (τ = 0.05 s).

Why it matters more than the position filter

Position error moves the overlay by a fixed number of metres. Orientation error moves it by an amount that grows with range: at 50 m, one degree of jitter swings a boundary 0.87 m sideways; at 150 m it is 2.6 m. Android's rotation vector wobbles by a degree or two even on a table, so an unfiltered pose is worth several metres of visible movement — considerably more than the raw GNSS jitter that was fixed first.

Interpolation is on quaternions, not matrices. Averaging rotation matrices element-wise does not produce a rotation: the result is not orthonormal and it shears the overlay rather than turning it. The matrix-to-quaternion conversion uses Shepperd's method, branching on the largest diagonal term — not an optimisation, but because the naive form divides by a value approaching zero for rotations near 180°, which is exactly a phone turned to face behind the agent.

The one subtle decision

The filter adapts on deviation from the current estimate, not on frame-to-frame angular rate. Jitter of a degree and a half arriving every 20 ms is an instantaneous rate of 75 °/s, which looks exactly like a deliberate pan and defeats a rate-adaptive filter completely. Deviation separates them cleanly: jitter is bounded by its own amplitude however fast it arrives, because the estimate sits in the middle of it, while a genuine turn makes the estimate fall behind and the gap grows until the filter speeds up to close it.

Field testing raised the deviation threshold from 10° to 25°. Walking is not a still phone with noise on top — each footfall pitches and rolls the handset several degrees and an arm swing adds more, so ordinary gait was reading as deliberate motion and the boundary jogged along with the walk. A deliberate pan is 60° or more and still clears the higher bar immediately.

05 · Heading fusion

core/heading/ · HeadingFusion.kt · CourseOverGroundDetector.kt
What it does

Establishes true north from something trustworthy, then carries it on the gyroscope. Three sources, ranked, each reported to the user by name with its own expected error.

Why the compass is not enough

A magnetometer near a tractor, a transformer, a steel gatepost or a phone case with a magnet is wrong by 15–25°. As FIG 08 shows, 20° at 80 m puts the boundary 29 m sideways — the middle of the neighbour's field, drawn confidently. So heading is never reported as a bare number; it always carries where it came from and how much to trust it.

The three sources

Course over ground (3–5°). Location.bearing is derived from GNSS motion, not from the magnetic field, so nothing on the ground can corrupt it. The detector accumulates a window and requires 20 m of walking, at least five samples, speed above 0.7 m/s, accuracy better than 25 m, no gap longer than 5 s — and a mean absolute bearing spread under 8°. That last test is what makes it safe: a window where the agent turned would average its two legs into a confident heading pointing between them, so the window is discarded outright rather than averaged.

Landmark snap (2–3°). The agent aims the crosshair at a feature whose coordinates are already cached — the plot's own access point — and taps. Both endpoints are known so the bearing is simply computable; the only correction is for the crosshair not sitting on the optical centre. Refused below 10 m, because at 3 m a 2 m error in your own fix is a 34° bearing error.

Magnetometer (15–25°). Fallback, and never a resting state. Once a fix exists the compass is demoted to trimming slow gyro drift — 300 s time constant, and a hard ±10° ceiling on how far it may ever pull a lock. Without that ceiling a magnetically disturbed site would walk a good lock onto the neighbouring field slowly enough that nobody notices.

Two sensors, one job each

TYPE_GAME_ROTATION_VECTOR has no magnetometer input: smooth, disturbance-proof, and arbitrary in absolute yaw. That is the carrier. TYPE_ROTATION_VECTOR knows where north is and feeds only the trim. Only the carrier is smoothed and only the carrier publishes a pose — running both through one filter was a real bug that quietly disabled the smoother, because the two attitudes sit tens of degrees apart in yaw and the deviation measure saturated permanently.

06 · What gets drawn, and why it is a wall

core/render/OverlayGeometry.kt · ui/ar/ArOverlay.kt
What it does

Each boundary edge is stood up into a vertical panel 2.6 m tall — eye height plus a metre — with a solid rail along its top and a post at each corner. Two modes: beyond 30 m from the nearest edge the plot is a filled shape with corner posts; inside 30 m the fill is dropped and each edge becomes a band as wide as the live GNSS accuracy.

Why not a line on the ground

The first build drew the boundary flat, and reviewers' first comment was that it read as a coloured carpet rather than a limit — a shape lying on the floor gives the eye no cue that it is an edge. A flat overlay also disappears entirely when the phone is held level, because the ground plane is then edge-on to the camera.

Wall height matters too. A wall topping out below eye level reads as floating: the eye takes the top rail for the boundary and the bottom edge for a shadow, because nothing connects it to the ground. Carrying it past eye level puts the rail against the sky or the far treeline, and the panel unmistakably stands on the earth.

The near mode, and honesty about error

A crisp line at 5 m is a false precision claim, and the first time a farmer disputes a reading it is the line that gets blamed. So inside 30 m the edge becomes a band whose half-width is the receiver's live accuracy, built in metres so perspective narrows it with distance on its own. Bands are suppressed once the agent is closer to the edge than the accuracy itself — a band 8 m wide seen from 6 m has its near side behind the camera and floods the whole frame.

Details that only field testing produces

Painter's ordering. Translucent panels composited in ring order let the far side of a plot paint over the near side, which looks like a crease. Walls are sorted far-to-near.

Fades with floors. A 2.6 m wall 3 m away subtends most of the frame, and a boundary you are standing against is the one you least need drawn over your view. Panels fade out below 8 m — but the rail never drops below 0.75 opacity, because the line is the boundary and losing it as you step up to the fence removes the answer at the moment you are trying to stand on it.

Dark backing strokes. Every rail, post and marker is drawn twice: a dark halo, then the colour over it. A single coloured line disappears wherever the background shares its luminance, and outdoor footage is mostly bright sky, pale soil and corrugated fencing. Road signs and map labels have been drawn this way for a century.

07 · The health grid — and the answer to "3×3 or 10×10?"

shared/src/health.ts · service/src/routes/health.ts
The short answer

Neither. The cell size is computed per plot, sized so that roughly fifteen cells span the plot's width, rounded to the nearest half metre and clamped between 2 m and 10 m. For the plot the team walked — PLT-7013, 886 m² — that comes out at 2 m cells on a 19 × 16 grid, of which 221 cells fall inside the boundary. It is not a fixed 3×3 and not a fixed 10×10.

Why it is adaptive

It used to be a fixed 10 m, matching Sentinel-2's native red/NIR resolution. That is right for a five-hectare field and useless for a small one: a 30 m plot came back as a 3 × 3 grid, which is not a map of anything — it cannot show where inside the plot a problem is, which is the only question the layer exists to answer. Worse, nine cells cannot form a hotspot at all, because a cluster needs three touching stressed cells, so small plots silently reported that they had no problems.

The clamps are not arbitrary in either direction. The 2 m floor exists because below the imagery's own ground resolution a finer grid is interpolation dressed up as detail. The 10 m ceiling exists because going coarser than the native resolution throws away measurements that were actually taken. And the half-metre rounding exists because the exact figure is a cache key — an irrational one would mean every request rebuilt the raster from scratch.

How a cell is built

The grid is laid out in metres, anchored at the polygon's south-west corner, so cells are square on the ground rather than square in degrees. A cell is kept only if its centre falls inside the boundary — which is what makes every hotspot centroid a legal walk-to target, since it is the mean of points each already inside the plot. Then the kept square is intersected with the boundary, because keeping a cell on its centre still leaves up to half of it hanging over the fence, and the layer's whole claim is that it describes this plot.

NDVI bands at 0.25 / 0.40 / 0.55 — the conventional break points, and deliberately conservative. Calling a healthy cell stressed sends an agent on a pointless walk, which is how a tool like this loses its audience.

08 · Hotspot clustering

shared/src/health.ts · findHotspots()
What it does

Flood-fills touching cells at severity 2 or worse into clusters, discards clusters smaller than three cells, then ranks them: worst band first, then largest, then lowest index value. A cluster's band is its worst cell, not its average — a patch with a dead centre matters more than its edges suggest.

Why four-way connectivity, not eight

Diagonal-only neighbours share a single corner on the ground. Chaining through them merges two genuinely separate problems into one hotspot and puts its centroid in the healthy gap between them — a walk-to point that is not a problem at all. Four-way keeps them separate and gives the agent two markers to visit.

Why ties break deterministically

The rank is what the field agent's route is built from. Two visits to the same plot must produce the same numbered markers in the same order, or the agent cannot trust that marker 1 means anything.

09 · One palette, two languages

palette.json → tools/gen-palette.mjs → palette.ts + PlotPalette.kt
What it does

palette.json is the single source of truth for every colour and opacity in both codebases. A generator reads it and writes the TypeScript and the Kotlin. Neither generated file is edited by hand, and CI can run the generator with --check to fail a build that drifted.

Why the colours are what they are

Both backgrounds this app runs against — satellite imagery of farmland, and a phone camera pointed at a field — are dominated by green and brown. There is no green in the plot palette: a green boundary on a green crop is the one combination guaranteed to disappear. White is included because the first field test happened after dark, where it reads better than any hue.

The severity ramp originally ran green → yellow → amber → brown, chosen so the bad end described the ground rather than alarming about it. Outdoors that reasoning failed on its own terms: amber and brown are the colour of dry soil, so the two worst bands were painting earth-colour onto earth and vanishing. A grading layer has to contrast with the ground it grades, not match it. The bad end is now red.

The guard, and why it is there

This mechanism failed silently once and it is worth recording. When the severity ramp was first added to the generator, the values were interpolated while editing the generator and pasted in as literals. The output looked perfect, --check passed forever after — because the generator and the files it wrote were equally stale — and a colour change committed to palette.json reached neither language. A build was shipped and field-tested with the old ramp.

The generator now asserts, before writing anything, that every colour in palette.json actually appears in each generated file, and exits with a named diff if not. The lesson generalises: a single-source-of-truth tool whose verification step is part of the same stale artefact verifies nothing.

10 · Offline-first cache and what sync actually costs

data/PlotRepository.kt · data/db/AppDatabase.kt
What it does

Room is the source of truth. Every screen reads from it and nothing on screen ever waits for the network. Sync is an explicit action: fetch plots within 5 km of the agent, replace the cached set, then fetch each plot's health raster concurrently, tolerating individual failures.

Design decisions worth defending

Rasters are a separate endpoint. A health snapshot is an order of magnitude larger than a boundary and has a different lifetime — a boundary is drawn once, a raster is re-derived whenever new imagery lands. Bundling them would force a re-download of every boundary to refresh one raster.

Raster failures do not fail the sync. The health layer is an extra. A sync that lands every boundary and misses one raster is a success; reporting it as a failure sends the agent hunting for signal they do not need. The counts are reported separately so a shortfall is visible rather than looking like plots that happen to be healthy.

An empty radius widens to everything. "0 plots near you" is indistinguishable on screen from "the sync failed", and the honest reading of an empty radius is usually that the boundary was drawn somewhere else.

Timeouts are short — 5 s connect, 8 s read. At a rural site the radio either works within a couple of seconds or it does not work at all, and a request hanging for thirty seconds is a spinner the agent watches instead of a cached plot they could already be walking to.

Sheet 07

Questions you'll be asked

The ones that came up in the demo, answered with numbers.

What grid size do we use — 3×3 or 10×10?

Neither; it is computed per plot. Cell size = √area ÷ 15, rounded to the nearest 0.5 m, clamped to 2–10 m. The plot we walked came out at 2 m cells, a 19 × 16 grid, 221 cells inside the ring, 2 hotspots. A fixed 10 m grid is what produced the useless 3 × 3 the question is remembering — see FIG 11.

How does the camera know where it is?

It does not. The camera is a backdrop with a known field of view and nothing more — no image processing, no feature tracking, no SLAM. Position comes from GNSS, filtered. Direction comes from the gyroscope, referenced to true north by a walked segment or a landmark tap. Those two plus the lens geometry are enough to project a known coordinate onto the right pixel. That is why it works at night and facing a blank wall, and why it cannot correct itself from what it sees.

How is distance computed?

Convert both positions into the local metric frame — multiply the latitude difference by 110,540 and the longitude difference by cos(lat) × 111,320 — then take the hypotenuse. The label on screen shows range to the plot centroid; the near/far mode switch uses the perpendicular distance to the nearest edge, which is the number that matters when you are walking up to a boundary.

How accurate is it, honestly?

Position: 3–5 m, the receiver's own accuracy, which the app displays. Heading: 2–3° after a landmark snap, 3–5° after a walked segment, 15–25° on the compass alone. Since sideways error is range × sin(heading error), expect roughly 1–2 m of lateral error at 30 m on a good lock. At the boundary itself the accuracy band is drawn to the receiver's live figure rather than a crisp line, so the drawing never claims more than it has.

How big is the app, and what does a visit cost in data?

12.8 MB debug APK, roughly 13 MB installed; a release build with minification will be smaller. All seven boundaries are 1.1 kB gzipped. A health raster is 0.8–8.4 kB gzipped depending on plot size. A full sync of the current dataset is about 25 kB. A plot visit after sync transfers nothing at all — the AR screen never opens a socket.

Does it need internet? Does it need ARCore?

Internet only to sync, and only until the cache is warm. ARCore is not used, not linked, and not required — the app runs on any Android 8.0 device with a gyroscope and GNSS, including handsets on Google's unsupported-for-ARCore list.

Is the crop-health data real?

No, and the system says so everywhere. It is deterministic synthetic NDVI seeded from the plot id, present so the whole path from raster to hotspot to a walk-to coordinate could be built and demonstrated. The API returns synthetic: true with an explanatory note and the app labels it on screen. Connecting real Sentinel-2 means replacing one function; every consumer downstream takes an index sampler and knows nothing about its source.

What happens when the heading is bad?

The overlay dims to 45% and greys, the chip says why, and the crop-health layer switches itself off entirely — a coloured patch drawn on the wrong ground is worse than no patch. The app asks for twenty metres of straight walking, or a tap on the access point, and re-locks.

Can the phone edit a boundary?

No, by design. One writer means no merge conflicts over where a fence runs. If a boundary is wrong, it is redrawn in the web tool and picked up on the next sync.

Sheet 08

Running it yourself

Web

  1. npm install at plot-web/ — one npm workspace root covering shared, service and web.
  2. npm run build:shared first, always. The other two workspaces compile against its emitted types, not its source.
  3. npm run dev:api and npm run dev:web in two terminals. With no Supabase credentials in the environment the API falls back to SQLite, so it runs with nothing to provision.
  4. npm run test:api for the 17 API tests. node tools/gen-palette.mjs --check fails the build if either generated palette has drifted from palette.json.

Android

  1. JDK 17 or 21. Gradle 8.11 cannot parse a JDK 26 version string, so set JAVA_HOME explicitly if a newer JDK is on the path.
  2. ./gradlew test runs all 125 unit tests on the JVM — no emulator, no device.
  3. ./gradlew assembleDebug -PapiBase=https://your-api/. The trailing slash is required by Retrofit. Without the flag the build points at 10.0.2.2, which is the emulator's route to the host and unreachable from a real handset.
  4. Debug builds include a simulation mode — a joystick and error sliders that drive the whole pipeline from synthetic sensors, so the overlay can be worked on at a desk. Release builds contain neither.

In the field

  1. Sync while you still have signal. Plots within 5 km, plus their health rasters.
  2. Open the plot and walk twenty metres in a straight line. The chip goes green and names the source. If you cannot walk it, aim the crosshair at the plot's access point and tap.
  3. Read the chip before believing the overlay. Green means a fresh fix; amber means it is being carried on the gyroscope and tells you for how long; grey means walk a few steps.
  4. Cycle the health layer with the layer button: off → problem areas → all cells. Problem areas is the default, because a plot is mostly healthy and painting every cell buries the two that matter.
  5. Walk to marker 1 first. Markers are ranked worst-first and the ranking is deterministic, so the same plot always numbers them the same way.
